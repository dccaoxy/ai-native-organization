刚才我们已经把 **Goal Protocol v0.1** 和 **Task Protocol v0.1** 基本冻结，并检查了两者之间的接口。然后正式进入了 **Work Protocol**。

我们停在这里：

> **Goal = 我们要让什么发生。**  
> **Task = 为了让它发生，现在需要交付什么。**  
> **Work = Human + Agent 实际如何把这个交付物做出来。**

而 Work 和前两个最大的区别是：**Goal 和 Task 需要比较强的结构化规则，Work 反而应该是整个系统自由度最高的地方。**

我们已经初步形成了 7 条 Work 原则：

1. 所有正式 Work 必须服务于一个 Active Task。
2. Human / Agent 在 Task Boundary 内拥有默认执行自主权。
3. **Protocol 固定，Workflow 不固定**——怎么完成，由执行者动态决定。
4. 一旦触碰资源、权限、风险、能力等 Boundary，就必须 Pause / Escalate。
5. 工作过程尽量由系统自动留痕，不要求员工大量写工作日志。
6. Work 过程中可以产生新的 Task Proposal、Goal Proposal 和 Knowledge。
7. Work 的终点只是 **Submit Output + Evidence**，执行者不能自己宣布 Task Completed。

然后我们正准备深入讨论 Work 最重要的问题：

> **Human 和 Agent 在 Work 里面究竟应该是什么关系？**

也就是一个 Human 领取 Task 后，到底应该是：

**Human Executor** —— 人主要干，AI辅助；

**Human + Agent Co-worker** —— 人和AI共同完成；

**Human Orchestrator** —— 人拆解、调度多个Agent，自己主要负责整合；

**Human Supervisor** —— AI主要执行，人主要监督、判断和验收。

而且我们已经发现这里不能简单规定“AI执行、人监督”，因为实验对象是新人。如果新人长期只监督自己根本不会做的事情，**Human Oversight Capability 可能根本建立不起来**。

所以我们下一步真正要设计的就是：

> **什么情况下 Human 应该亲自做？什么情况下应该 Human + AI 共做？什么情况下可以让 AI 大量执行？随着人的能力成长，这个比例是否应该动态变化？**

这正好把 **Work Protocol、Learning 和 Human-Agent Capability** 三件事连接起来了。我们可以从这里继续。

这个困惑非常合理，而且我重新看我们前面的定义后，觉得**我们可能把 Work“对象化”得太重了**。

最简单的区分其实只有一句话：

> **Task 是一份“要交什么”的契约；Work 是为了交出来而实际发生的过程。**

比如你给一个新人这样一个 Task：

> **Task：**  
> 找出影响新人 AI 学习速度最大的 5 个因素。  
> 7 天完成。  
> 至少分析 20 名新人数据。  
> 每个结论必须有 Evidence。

这个东西可以被系统保存、领取、派发、验收。

新人领取以后，真正发生的事情可能是：

> 上午和自己的 Agent 商量怎么分析；  
> Agent 去整理数据；  
> 自己看结果发现数据不够；  
> 找另外一个 Agent 查资料；  
> 下午访谈两个新人；  
> 推翻上午的假设；  
> 第二天重新分析；  
> 最后形成 5 个因素和 Evidence。

这一大堆过程就是 **Work**。

所以：

**Task 是名词。**

**Work 更接近动词。**

---

### 用我们现在这套体系来看就特别清楚

比如：

> **Goal**  
> 8周内让新人达到 AI 能力标准的平均时间降低30%。

下面产生：

> **Task**  
> 找出影响新人学习速度最大的5个因素，并提供证据。

然后才发生：

> **Work**  
> 小王 + Agent 怎么研究、分析、访谈、推翻假设、重新尝试……

最后：

> **Output + Evidence**  
> 5个因素 + 数据依据。

所以其实是：

**Goal**
> 为什么以及最终要改变什么？

↓

**Task**
> 现在需要交付什么？

↓

**Work**
> 实际怎么把它做出来？

↓

**Output + Evidence**
> 最终交出了什么？

---

而且这让我觉得，我们接下来可能**根本不需要设计一个很重的 Work Protocol**。

因为我们前面一直强调：

> **固定 Protocol，不固定 Workflow。**

真正需要严格管理的是：

**Task 的输入和输出。**

也就是：

`Task`
→ Expected Output  
→ Acceptance Criteria  
→ Boundary

以及：

`Submission`
→ Output  
→ Evidence

至于中间 Work 怎么发生，反而应该尽量自由。

---

### 我甚至建议修改我们刚才那张 Operating Loop

现在写的是：

`ACTIVE TASK`

↓

`TASK BUS`

↓

`Human / Agent Unit`

↓

**WORK**

↓

`Output + Evidence`

这个逻辑没错。

但 **WORK 不需要像 Goal、Task 一样成为一个重型系统对象**。

它更像一个“自由执行区”：

```text
                TASK
        ┌──────────────────┐
        │ Expected Output  │
        │ Acceptance       │
        │ Boundary         │
        └────────┬─────────┘
                 ↓

        ┌──────────────────┐
        │                  │
        │       WORK       │
        │                  │
        │ Human + Agent    │
        │ 自由选择方法      │
        │ 自由组织 Workflow │
        │ 动态调用工具      │
        │ 动态产生 Subtask  │
        │                  │
        └────────┬─────────┘
                 ↓

        Output + Evidence
                 ↓
              Review
```

系统真正约束 Work 的可能只有三件事：

> **不要偏离 Task。**  
> **不要突破 Boundary。**  
> **最后必须产生可验收的 Output + Evidence。**

剩下的尽可能自由。

---

而且这里还有一个概念我们之前有点混用了：**Subtask。**

假设 Task 是：

> “找出5个影响新人学习速度的因素。”

执行过程中小王可能让：

Agent A → 清洗数据  
Agent B → 查文献  
Agent C → 整理访谈

这些事情**不一定都需要成为 Task Bus 里的正式 Task**。

它们可以只是：

> **Work 内部的临时 Subtask / Agent Call。**

只有当某件事情需要：

**独立责任人、独立资源、独立验收、跨人协作，或者需要进入组织级调度**

时，才“升级”为正式 Task。

否则 Task Bus 很快会充满：

> “查资料”  
> “整理Excel”  
> “让Agent总结”  
> “开会”

几万个微任务。

这会非常糟糕。

---

所以你这一问反而帮我们把架构变简单了。

我现在倾向于：

> **Goal 和 Task 是组织级对象。**
>
> **Work 是 Task 内部的自由执行空间。**
>
> **Workflow / Agent Call / 临时 Subtask 属于 Work 内部，不默认进入组织级 Task Bus。**

只有需要组织级协调的东西才提升为 Task。

这样以后员工的体验也会简单很多：

> **组织告诉我：你要交什么、什么叫合格、边界在哪里。**
>
> **至于怎么做——我和我的 Agent 自己决定。**

我认为这可能比我们刚才试图设计一整套复杂的 **Work Protocol** 更符合我们最初的 AI-native 思想。

> 产生重要中间产物 → 发一次  
> 遇到阻塞 → 发一次  
> 完成 → 发一次

再加一个低频保活。

---

### 3. 对“能接入协议”的 Agent，可以自动监控

这是最理想情况。

比如 Agent 本身支持：

API、MCP、Function Calling、插件、CLI。

那它可以自动：

> 领取任务 → ACK → 工作 → Heartbeat → Submit

这时 Task Orchestrator 基本可以知道它是否仍然有效执行。

---

### 4. 对“封闭式 Agent”，不能假装自动化

比如某员工只是打开一个普通聊天窗口使用某个 AI 产品，而这个产品：

> 不支持你的 Organization Gateway  
> 不支持 API  
> 不支持 MCP  
> 不支持回调

那中央系统**根本不知道它有没有在工作**。

这时候就不能叫真正的 Organizational Agent。

它只能算：

> **Personal AI Tool**

这类场景下，由 Human 作为 Executor Unit 的正式责任人。

也就是中央系统只看：

`Human ACK`
`Human Checkpoint`
`Human Submit`

至于他背后用哪个 AI，组织不监控。

这个区别很重要：

> **能接入 Organization Protocol 的 Agent = 可管理的组织节点。**
>
> **不能接入的 Agent = Human 的私人辅助工具。**

---

### 5. 所以我们可能需要定义三种 Agent 等级

我觉得这个很值得写进设计。

**Managed Agent**

完全接入 Task Bus。

系统可以知道：

任务状态、Heartbeat、调用记录、输出、资源消耗。

**Connected Agent**

可以提交 Task 状态和结果，但看不到完整运行状态。

**Unmanaged Personal Agent**

中央系统无法直接观察。

组织只管理 Human Executor。

这样我们不会假装所有 Agent 都一样可控。

---

### 6. 还有一个非常重要的设计原则

不要把：

> **“Agent 在线”**

当成：

> **“Task 正在有效推进”。**

一个 Agent 进程活着，但可能一直循环、卡住、产生垃圾。

所以真正应该监测的是：

> **Progress Signal**

比如：

是否产生新的 Artifact  
是否产生 Evidence  
是否完成 Checkpoint  
是否推进依赖  
是否调用相关 Knowledge  
是否提交中间结果

所以：

**Alive ≠ Productive**

Task Orchestrator 真正要判断的是：

> **Is this task making credible progress?**

---

所以我会把我们前面的 `Stalled Detection` 改得更准确一点：

> **Task Orchestrator 不负责检测 Agent 是否“活着”，而负责检测 Task Lease 是否有效、是否存在可信进展。**

技术上就变成：

`Task Lease`
+
`Heartbeat / Event`
+
`Progress Signal`
+
`Timeout Policy`

这套设计特别适合你现在这种**分布式 Agent 环境**。

而且它进一步印证了我们之前那条架构原则：

> **不要统一 Agent。**
>
> **统一协议。**

Agent 可以在员工电脑里、云端、ChatGPT、Claude、Codex、企业 Agent 里各自运行。

组织真正控制的是：

**Identity、Task、Lease、Boundary、Evidence、Review、Audit。**

这才是分布式 AI-native 组织能成立的基础。

这一层开始越来越需要 Judgment。

> **越往这一层走，Human Acceptance 的价值越大。**

| Review Dimension | 它问什么？ |
|---|---|
| Completeness | 交齐了吗？ |
| Compliance | 做的是要求的事情吗？ |
| Evidence | 证据支撑结论吗？ |
| Correctness | 结果正确吗？ |
| Quality | 结果足够好吗？ |
| Risk | 有没有隐藏问题？ |
| Confidence | Reviewer 自己有多确定？ |

> **不是每个 Task 都需要七项全部 Review。**

> 把1000条数据按照明确规则分类。

可能需要：

**全部七层。**

> **Review Profile**

告诉 Review Agent：

> **这个 Task 应该检查什么，以及检查到什么深度。**

我现在不急着把它写进 Task Schema，因为我们还在讨论。

> **Review 不应该重新做一遍 Task。**

> **用尽可能低的成本，获得足够高的错误发现概率。**

所以未来可能会出现：

**抽样检查、交叉验证、重新计算关键数字、寻找反例、检查 Evidence、测试关键假设**

> **Review Cost 与 Error Detection Rate 之间的最优关系是什么？**

**Insight**

**Usefulness**

是否具备合理可行性？

**Decision Readiness**

这个结果是否已经足够支持下一步行动？

`Insight 4/5`

> **某个结果从“候选结果”变成了“组织正式认可的结果”。**

因此必须强制留痕。

这也提醒我们：**Audit Protocol 其实还没有正式设计。**我们之前一直提到 Audit Trail，但没有系统讨论。它可以放在后面作为一个横向基础协议单独设计，不必现在打断主线。
